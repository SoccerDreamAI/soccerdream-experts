# 架构说明

[English](../architecture.md) · 简体中文

## 形态

```
                 ┌──────────────┐
   赛事事件 ─────▶│    上下文     │  统一单位、统一时间窗、来源优先级
                 └──────┬───────┘
                        │  一份规范化记录
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  专家 A  │   │  专家 B  │   │  专家 C  │   ← 彼此独立，不共享上下文
  └────┬─────┘   └────┬─────┘   └────┬─────┘
       └──────────────┼──────────────┘
                      ▼
              ┌───────────────┐
              │   是否一致？   │
              └───┬───────┬───┘
             一致  │       │  不一致
                  │       ▼
                  │  ┌──────────────┐
                  │  │    质询环节   │  冲突主张正面对撞
                  │  │   (1..N 轮)  │  必须有一方让步，否则并列「未决」
                  │  └──────┬───────┘
                  ▼         ▼
              ┌───────────────┐
              │     复盘      │  对抗式审计，有权推翻结论
              └───────┬───────┘
                      ▼
              结论 + 置信度 + 引用证据
```

## 为什么必须严格独立

每位专家拿到的都是同一份规范化记录，除此之外没有别的。没有共享草稿，没有滚动摘要，也没有「其他人是这么想的」。

这不是审美偏好。**专家 B 一旦看到 A 的草稿，B 的输出就不再是独立估计，而变成了对 A 的修订。** 两份相关的估计看起来像「一致」，实际只携带一份的信息量。你付了四个专家的成本，只收到一个。

代价是真实的：独立运转的专家会产出更混乱、更互相矛盾的输出。而这份混乱**本身就是信号**。

## 为什么禁止取平均

处理四份冲突研判最顺手的办法是取平均。它也是最保证你什么都学不到的办法。

设想两位专家：一位认为分布窄且低，另一位认为宽且高。平均之后得到一个居中、宽度中等的分布——这个形状**两个人谁都没提过，谁也不会为它辩护**。你凭空造出了一个没有任何参与者相信的结论，同时销毁了这次运行中唯一真正有信息量的事实：两个了解情况的人，分歧很大。

取平均还有一个不对称的毛病：**一致时它是个空操作，零成本；分歧时它破坏性最强。** 也就是说，这个操作只在「你最需要保住分歧」的那个场景里才真正生效。

质询环节问的是取平均问不出的问题：**哪一条主张能指出自己的证据？** 质询是一场引用比拼，不是投票。一条主张能活下来，是因为它引了两条独立数字；被否掉，是因为它引的是一句感觉。败方必须明确让步，并且这次让步会被记录。

如果双方都不让步，两条主张并列标记为 `unresolved`，这个标记会一路带到发布。一句诚实的「这事我们没定下来」，比一个伪造出来的中间值有用得多。

## 为什么评审员有权推翻结论

复盘是唯一读到成品稿的环节，而且它有**推翻**结论的权力，不只是提意见。

没有权力的评审员产出的是「建议性批注」，在截止日期面前必然被忽略。有权力则会引入另一种失败模式——它能杀掉好结论。所以我们把评审员的动作设计成**机械的、有固定顺序的**，而不是靠判断力：五项固定审计，按序执行，每项都对着具体句子产出 diff。

一次运行**允许以「无结论」收场**，并且照实发布。相比之下，发一个评审员自己都辩护不了的结论更糟——而这恰恰是大多数分析产品的失败模式。

## 本仓库不包含什么

训练层、评估权重、实时数据适配器，跑在托管服务上。本仓库包含理解一次运行**形态**所需的全部内容，以及用同一套 schema 搭自己团队所需的一切。它不包含让托管版置信度数字变得可信的那套校准。

我们把这句话明说，是因为另一种做法——发一个看起来完整、其实不完整的仓库——对这个项目的伤害，远大于缺失的代码本身。

## 我们踩过的坑

记在这里，因为这才是架构文档里有用的部分。

| 失败模式 | 症状 | 根因 / 修法 |
|:--|:--|:--|
| 独立性泄漏 | 专家们「一致」得可疑地频繁 | 共享上下文是从运行时串进去的，不是从提示词 |
| 评审橡皮章 | 多轮运行零推翻 | 评审员读到的是已经排版好的成品，而非草稿 |
| 人设塌缩 | 两个「不同」专家输出几乎一样 | 双方的先验都是「要谨慎、要多方面考虑」的换皮 |
| 置信度虚高 | 单来源主张也给了高置信 | 置信度是成员自报，没有对着引用审计做校准 |
| 质询走过场 | 分歧永远一轮解决，且总是同一方让步 | 挑战者没有证据标准，所以它永远先让 |

五个里四个是提示词问题，不是代码问题；只有第一个是结构性的。调自己团队的时候，记住这个比例。
